A real OpenID Connect provider, small enough to forget about.

Authorization code with PKCE, signed RS256 ID tokens and a one-click sign-in page. Built for local development and end-to-end tests, where Google has no sandbox and Dex wants a password.

docker run --rm -p 5556:5556 curroya/oauth2-mock

Then point your client at http://localhost:5556 with local-client / local-secret. More setups

localhost:5556/auth?response_type=code&code_challenge_method=S256&…

Your client runs for real. Only the person signing in is fake.

Discovery, PKCE, code exchange and ID-token verification all happen against a working provider. What you skip is a Google account and a password field.

  • Any email signs in

    No user list to keep in sync with your tests. List users only when you want buttons, fixed ids or names.

    login_hint=worker-7@example.test

  • Same email, same id

    An email without an id gets a SHA-256-derived UUID, identical on every restart and every machine.

    sub = uuid(sha256(email))

  • A key that survives restarts

    The RSA key comes from a seed, so restarting the mock never invalidates the keys your backend cached.

    KEY_SEED=oauth2-mock

  • One issuer, two hosts

    Keep iss as your backend sees it and serve the browser from another host. No /etc/hosts edits.

    http://oidc:5556 ↔ http://localhost:5556

  • Strict where it matters

    PKCE S256 is mandatory and codes are single-use. A wrong verifier or redirect fails the way production would.

    400 invalid_grant

  • Tested with a real client

    The test suite drives the full flow with the Rust openidconnect crate, not hand-written requests.

    tests/flow.rs

What happens on a sign-in

Standard authorization code with PKCE. Nothing your client does is skipped.

  1. Your backend

    Discovers the provider

    GET /.well-known/openid-configuration · GET /keys

    Endpoints and the public key, cached like any production provider.

  2. Browser

    Opens the authorization page

    GET /auth?code_challenge=…&nonce=…&state=…

    A request without an S256 challenge gets 400.

  3. Person

    Picks a user

    POST /auth login_hint=… → 303 /callback?code=…

    A click, a typed email, or a login_hint on the first request, which skips the page.

  4. Your backend

    Exchanges the code

    POST /token → id_token (RS256)

    Client, redirect and verifier are checked before a signed ID token comes back.
